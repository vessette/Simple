Project roadmap · Sales, Enrollment & Subscriptions

Vick: an AI sales agent that earns its autonomy

Vick is an AI employee for a training company's sales team: finding and sorting leads, following enrollments through to payment, and keeping renewals and revenue reporting honest. This roadmap covers how it's specified, what's built, what's next, and the governance that keeps every capability a draft until an accountable person approves it.

        04

        Problem and goals

        The problem

        • The sales manager runs lead follow-up, enrollment support and renewals largely by hand, across several admin screens.
        • 16 older automated jobs touch sales, with unclear owners. One was set up to approve leads and add them to cold email campaigns with nobody reviewing.
        • Analyst reporting on revenue and enrollment is manual and hard to trace back to source.
        • The platform couldn't show who decided a lead's offer, so a person's choice could be silently overwritten.

        Goals

        • Specify 32 capabilities for one AI employee, each with an autonomy ceiling, a human decision point and evidence of correctness.
        • Build capabilities as tested, suggest-only drafts first, then promote them one rung at a time on evidence.
        • Give the accountable manager one place to see and approve what the agent prepares.
        • Settle every inherited automation: migrate, supersede, retire or assign an owner.

        Non-goals

        • The agent never sends email or messages itself. Outbound contact is denied by default platform-wide; a person sends.
        • No refunds, voids, cancellations or free seats without a human decision on every case.
        • No change to another domain's code without a change request to its owners.
        • No autonomy granted because a story was finished. Progress isn't authority.

        Design constraints

        • Every figure on screen comes from a live endpoint or is labelled missing. No invented numbers.
        • Unknown is a real answer. Logic is three-valued, and a missing input never silently counts as a pass or fail.
        • Every external call has a timeout and capped retries. Failed lookups write nothing.
        • Every side effect is idempotent: running it twice changes nothing the second time.

        06

        Governance model

        Each capability sits on a ten-rung autonomy ladder. The research sets a ceiling for each one; nothing climbs until a named person approves it. Bars show how many of the 32 capabilities have each rung as their draft ceiling.

        Rules the platform enforces

        • Tools are the throttle. With no tools granted, any approved level above R2 is forced back to R2.
        • Production needs a pilot. Reaching production takes a separately approved supervised pilot (R6), never approval alone.
        • Per capability, never per agent. One capability's level can't raise another's.
        • R8 doesn't exist yet. The platform has no coordinated handoff between agents, so no ceiling uses it.

        Rules this project adds

        • A ceiling is a draft until the accountable manager reviews it. Today none is approved.
        • Every capability names its human decision point and what evidence proves it worked.
        • Money decisions are capped at R2: a person decides each refund, cancellation and free seat.
        • Any legacy job that acts with no named human is superseded by one that prepares work for approval.

        09

        Engineering practice

        Build, break, harden

        Every capability is built for the happy path, then deliberately broken (rate limits, server errors, malformed responses, missing inputs, repeats), and each break gets a fix and a test that reproduces it. Mutation checks in scratch copies confirm the tests actually fail when a guard is removed.

        Delivery workflow

        Story prompt, then a branch, a pull request, review and merge. Criteria are ticked on main only after the merge is confirmed to contain the work. Only one open pull request touches the session log at a time, which removed merge conflicts after the first week.

        Traceability

        Every change is logged with its date, what changed and the verification evidence. Claims about the platform cite the file and line they came from at a pinned commit, and anything not verified is marked unknown.

        Safety by default

        Tokens are never stored or committed. Production questions go out as read-only, counts-only queries for an owner to run. No step in the project sends a message, books a meeting, enables an agent or grants a tool.

        13

        Success criteria

        A story is done when

        • Every acceptance criterion genuinely passes, not just the important ones.
        • Tests cover the happy path and at least one failure path.
        • A commit names the story and the work is merged to main.
        • No secrets in code, commits or logs.

        A capability is ready to promote when

        • The accountable manager has set its pass mark. (Pending: asked in the check-in.)
        • It meets that pass mark in shadow mode against her own decisions.
        • Its failure paths and switch-off triggers are written down.
        • A named person approves the next rung, and only that rung.

        Demo Day, 28 January 2027
